## Cambios aplicados

### Integridad de partidas y recuperación

- Las escrituras SQLite se serializan y se confirman mediante un comando Rust que utiliza una única transacción SQLx. Un fallo intermedio revierte el lote.
- Las colas esperan las escrituras en vuelo, conservan la última instantánea fallida y permiten reintentar. La cola de archivos usa sustitución temporal y renombrado.
- Un error de cuota web conserva el guardado anterior. La interfaz muestra el error y ofrece reintentar.
- El cierre nativo espera guardado y checkpoint; ante fallo mantiene abierta la aplicación. Se limpian los temporizadores del cierre.
- Los errores de lectura o JSON dañado bloquean las escrituras y muestran recuperación de carga. Un timeout de hidratación no autoriza sobrescribir datos.
- Cambiar de realidad espera el historial antes de activarla. Las respuestas tardías no reactivan slots anteriores ni marcan como cargados historiales descartados.
- Exportar una realidad inactiva carga también su historial. Si la lectura falla, no se genera una copia aparentemente válida pero incompleta.
- Importar sobre la realidad activa actualiza también la temporada en memoria, evitando que el estado anterior reemplace lo importado.

Archivos principales: `lib/desktopSqlite.ts`, `lib/desktopSqliteStorage.ts`, `lib/desktopStorage.ts`, `src-tauri/src/storage.rs`, `components/PersistenceNotice.tsx`.

### Seguridad de entradas y dependencias

- Codec compartido para formatos comprimidos con límites de entrada y de bytes realmente descomprimidos, decodificación UTF-8 estricta y liberación del lector.
- Validación de estructura, referencias y campos anidados antes de importar: equipos, series, partidos, temporadas, metadatos, recaps, historiales, entrenadores y mercado.
- Rechazo de claves de prototipo, profundidad excesiva, números inválidos, series vacías y progreso del draft fuera de rango.
- Los libros Excel se inspeccionan mediante streaming antes de materializar XML y celdas: límite de 64 MiB de archivo, 128 MiB descomprimidos y 10.000 miembros ZIP.
- CSP de escritorio y del servidor de previsualización: scripts propios con hashes, orígenes de conexión definidos y sin objetos embebidos.
- Dependencias y lockfiles actualizados. La auditoría npm pasó de 13 alertas, incluida una crítica, a cero alertas publicadas en la comprobación realizada.

Referencias técnicas utilizadas: [CSP de Tauri](https://v2.tauri.app/security/csp/), [migración a Next.js 16](https://nextjs.org/docs/app/guides/upgrading/version-16), [streaming de JSZip](https://stuk.github.io/jszip/documentation/api_zipobject/internal_stream.html).

### Rendimiento y estructura

- Pantallas secundarias cargadas mediante importación dinámica.
- Persistencia diferencial: se evitan reescrituras de temporadas e historiales sin cambios; caché por referencia de cada realidad.
- La compactación completa de SQLite queda como mantenimiento explícito, fuera del cierre habitual.
- Workers con limpieza de peticiones, tratamiento de errores de clonación, timeout y recuperación.
- Corregidos hooks condicionales, referencias modificadas durante render y dependencias de memoización.
- Separadas comparación del Hall, elementos compartidos, tipos del store, codificación de persistencia y codec de torneos.
- Concurrencia de Vitest limitada a cuatro workers para evitar saturación en la suite.

### Herramientas

- `npm run lint` usa ESLint real; se elimina el comando obsoleto `next lint`.
- `npm start` sirve la exportación estática `out/`.
- Añadidos `typecheck`, `check`, Playwright y CI para web y Windows.
- Node mínimo documentado: 22.12.
- Las únicas excepciones globales de lint de React/Next están explicadas: imágenes de exportación estática y análisis específico de React Compiler, que no está habilitado.

Los cinco flujos de navegador comprueban: serie y recarga; rechazo de importación sin alterar guardado; temporada con 60 equipos; cuota llena, reintento y recarga; JSON dañado, bloqueo y recuperación.

Las pruebas nativas usan un pool SQLite real en memoria y MockRuntime de Tauri: verifican enrutamiento/deserialización del comando IPC, acceso al pool, rechazo de otra ventana y rollback. Las pruebas de ciclo de cierre inyectan fallos y demoran I/O para comprobar que la ventana no se destruye antes de tiempo.

### Mediciones

- 100 realidades y 10.000 entradas históricas sintéticas: **10.201 escrituras iniciales → 1 escritura** al persistir una configuración sin modificar temporadas ni historial. Es una medición de amplificación de escrituras, no un benchmark de disco físico.
- JavaScript inicial observado en Edge: **1.437.988 bytes decodificados**, aproximadamente 1,44 MB. Se añade un presupuesto de regresión de 3 MiB. No se presenta como mejora porcentual porque no se conservó una medición inicial comparable.
- Se mantiene la prueba existente de codificación de recaps con unos 150 partidos y caché caliente.

## Límites de lo verificado

- Se ejecutaron navegador Edge, pruebas nativas e integración IPC; no una instalación interactiva completa ni todos los WebViews/sistemas operativos.
- CI está configurado; no se ha ejecutado en un proveedor remoto desde esta sesión.
- Cero alertas npm no significa ausencia de vulnerabilidades desconocidas ni una auditoría exhaustiva de cada dependencia Rust.
- La prueba de volumen es sintética. No se han usado las partidas personales del usuario ni simulado décadas de una partida real durante la auditoría.
- No se ha realizado una auditoría integral visual o de accesibilidad de todas las pantallas.
- La previsualización web aplica CSP; un alojamiento externo debe configurar también sus cabeceras.
